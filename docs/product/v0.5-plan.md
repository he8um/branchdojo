# BranchDojo v0.5 Plan

## Status

In development. `bisect-basic` is implemented on `main` as unreleased v0.5 work.

## Objective

Add deterministic debugging practice while preserving BranchDojo's disposable local repositories, final-state validation, and safety model.

## Product Theme

Deterministic debugging practice and exercise foundation hardening.

## Target Users

- Developers who have completed the beginner, intermediate, and v0.4 advanced exercises.
- Developers who need practical Git debugging workflow practice.
- Mentors and onboarding programs that want a local exercise for identifying regressions.
- Teams that want repeatable debugging drills without dashboards, telemetry, or remote services.

## Problems To Solve

- BranchDojo does not yet teach finding the commit that introduced a regression.
- Bisect workflows can drift into shell scripts or brittle command-sequence validation.
- Advanced validators now share patterns around refs, reachability, history shape, and content-at-ref checks.
- Future advanced exercises need a clearer boundary between useful internal helper reuse and premature external exercise infrastructure.

## Proposed Scope

- Add `bisect-basic` as the main v0.5 exercise.
- Use a deterministic local regression fixture with no network access or external dependencies.
- Validate a final diagnosis artifact and repository cleanup state, not the exact commands used.
- Add only the smallest internal helper hardening needed for deterministic advanced validators.
- Add progress-aware hints for bisect-style workflows.
- Keep Markdown report compatibility through the existing report renderer.
- Preserve the current CLI surface and JSON output shape.

## Explicit Non-Goals

- No external exercise packs.
- No custom exercise definitions.
- No YAML, TOML, or JSON exercise parser.
- No dashboards.
- No telemetry.
- No GitHub integration.
- No TUI or GUI.
- No new report formats.
- No HTML or PDF reports.
- No report templates.
- No command-history tracking.
- No shell-history inspection.
- No global Git config changes.
- No mutation outside BranchDojo workspaces.
- No release automation.
- No crates.io publishing unless separately planned later.

## Primary Exercise: bisect-basic

### Purpose

Practice identifying the commit that introduced a regression using Git history investigation.

### Difficulty

Advanced.

### Category

Debugging.

### Starting State

The generated repository starts on `main` with a clean working tree and a short linear history:

1. `Initialize sample app`
2. `Add stable login flow`
3. `Add checkout calculation`
4. `Introduce discount regression`
5. `Update copy text`
6. `Refactor display labels`

The regression should be represented by repository files, not a network service or external tool. A simple file marker can change from `discount_total=correct` to `discount_total=incorrect`.

### User Task

Investigate history, identify the regression-introducing commit, record the answer in a deterministic artifact such as `diagnosis.md`, and leave the repository in the expected final state.

### Expected Final State

- The repository is on `main`.
- The working tree is clean.
- No active bisect, merge, rebase, cherry-pick, or revert operation remains.
- `diagnosis.md` records the seeded culprit commit evidence.
- The regression does not need to be fixed in v0.5; identification is the exercise goal.

### Required Checks

- Metadata exists and is valid.
- Git repository exists.
- Current branch is `main`.
- Working tree is clean.
- No active Git operation remains, including bisect state.
- `diagnosis.md` exists.
- Diagnosis identifies `Introduce discount regression` or another stable culprit marker.
- Expected exercise files remain present.

### Warning Conditions

- The answer is correct but records only a less-ideal form of evidence such as a valid hash without the subject.
- The answer is correct but lacks supporting detail.
- A diagnostic branch exists even though the final branch is correctly `main`.

### Failure Conditions

- Diagnosis artifact is missing.
- Diagnosis names the wrong commit.
- Working tree is dirty.
- Repository is on the wrong branch when final design requires a branch.
- A bisect or other Git operation is still active.
- Expected files or metadata are missing.

### Progress-Aware Hint Ideas

- If `.git/BISECT_LOG` or related bisect state exists, suggest finishing or resetting bisect before checking.
- If HEAD is detached, suggest returning to the expected branch after recording the answer.
- If the diagnosis artifact is missing, suggest recording the suspected culprit commit.
- If the diagnosis is wrong, suggest comparing good and bad file markers across history.
- If the working tree is dirty, suggest committing, stashing, or discarding diagnostic changes.

### Report Considerations

Markdown reports should show diagnosis checks separately from cleanup checks and warnings. No report-specific code should be needed.

### Safety Considerations

- Do not require `git bisect run`.
- Do not require shell scripts.
- Do not require network access.
- Do not mutate anything outside the BranchDojo workspace.
- Configure Git identity only inside generated repositories.
- Validate observable repository state and recorded evidence, not shell history.

### Test Strategy

- Setup creates the deterministic linear history.
- Initial check fails with missing diagnosis.
- Correct diagnosis passes.
- Wrong diagnosis fails.
- Dirty working tree fails.
- Active bisect state fails or warns according to final policy.
- Detached HEAD cleanup follows final branch policy.
- JSON output remains compatible.
- Markdown report includes metadata and diagnosis checks.
- Hints mention missing diagnosis and active bisect state.
- Reset recreates the exercise.
- Regression tests continue covering all nine released exercises plus unreleased `bisect-basic`.

### Risks

- The exercise could become too procedural if validation depends on exact commands.
- Shell-script-based checking would weaken cross-platform support.
- Hash-only answers can be brittle if fixture history changes during development.
- Combining diagnosis and fix in one exercise could blur the learning objective.

### Open Questions

- Should the final state require ending on `main`, or allow ending on a diagnostic branch?
- Should the expected final state use `diagnosis.md`, `culprit.txt`, or another artifact?
- Should the validator accept commit subject, stable marker, short hash, full hash, or multiple forms?
- Should the generated regression check be only text fixtures, or include a portable command suggestion?
- Should `branchdojo check` require the regression to be fixed, or only identified?
- Should revert/fix after diagnosis be a separate future exercise?

## Deterministic Regression Fixture Plan

Prefer a file-based fixture. For example, `check.txt` can expose a stable marker such as `discount_total=correct` before the culprit commit and `discount_total=incorrect` after it. The generated README can suggest inspecting history and file contents without requiring scripts.

If a helper command is included, it should be optional, portable, and documented as a convenience rather than required validator behavior.

## Validation Foundation Plan

Potential internal helper hardening:

- Check file contents at refs.
- Check reachable commit subjects.
- Check branch ancestry.
- Check known good and bad commit markers.
- Check active bisect state.
- Normalize text consistently across platforms.

Only add helpers when implementation shows real duplication or risk.

## Hint Compatibility Plan

Extend the existing progress-aware hint router with lightweight `bisect-basic` guidance. Hints should remain read-only and deterministic.

## Report Compatibility Plan

Use the existing metadata-backed Markdown report renderer. Do not add report templates, JSON report files, HTML, or PDF output.

## Learning Path Impact

The advanced path should list v0.4 exercises as released and `bisect-basic` as unreleased v0.5 debugging practice while v0.5 remains in development.

## CLI Impact

No CLI surface changes are planned. `branchdojo list` includes `bisect-basic` while v0.5 development is in progress.

## JSON Output Impact

No JSON schema changes are planned. New check IDs may be added only when the validator is implemented.

## Safety Impact

v0.5 must preserve the existing workspace guard, unsafe path refusal, reset guard, local-only Git identity, and no global Git config changes.

## Testing Strategy

- Preserve the full existing test suite.
- Add setup, pass, failure, warning, hint, report, JSON, and reset tests for `bisect-basic` during implementation.
- Include no-regression tests for all nine released exercises plus unreleased `bisect-basic`.
