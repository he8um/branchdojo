# v0.2 Development Plan

## Goals

BranchDojo v0.2 should expand from beginner recovery drills into intermediate local Git workflows while keeping the product a kata tool.

The release should:

- Add a small set of intermediate exercises.
- Preserve disposable local repository generation.
- Preserve final-state validation.
- Preserve the v0.1 safety model.
- Keep commands, output, and result statuses stable unless a change is required by a documented exercise need.

## Non-Goals

v0.2 should not include:

- Network features.
- GitHub API integration.
- TUI or GUI.
- Custom external exercise packs.
- Generated result reports.
- Release automation.
- Exact command sequence validation.
- Shell history tracking.
- Work inside existing non-BranchDojo repositories.

## Exercise Candidates

### `stash-switch`

Implemented. Practice preserving local work before switching to another branch, completing feature branch work, and restoring the original work safely.

### `cherry-pick-basic`

Implemented. Practice moving one specific commit from a source branch onto the intended target branch without bringing unrelated work.

### `detached-head-recovery`

Implemented. Practice recovering work committed on detached HEAD by making it reachable from a named branch.

## Implementation Order

1. Design validator rules for `stash-switch`. Done.
2. Implement `stash-switch` setup, generated README, static hints, and tests. Done.
3. Design validator rules for `cherry-pick-basic`. Done.
4. Implement `cherry-pick-basic` setup, generated README, static hints, and tests. Done.
5. Design validator rules for `detached-head-recovery`. Done.
6. Implement `detached-head-recovery` setup, generated README, static hints, and tests. Done.
7. Revisit hint quality after all exercise validators are stable.

Progress-aware hints may be explored after the exercise validators are implemented and tested, but they should not block the first v0.2 exercise work.

## Validation Risks

- Stash workflows can leave no durable history signal, so validation should focus on final branch content, clean state, and absence of misplaced work.
- Cherry-pick workflows can be solved through patch-based commits, so validators should distinguish required final state from ideal history shape.
- Detached HEAD recovery requires reachability checks, which should verify that expected work is reachable from the intended branch.
- Warning checks should never hide missing required content, dirty working trees, active Git operations, or missing branches.

## Safety Considerations

v0.2 must keep the v0.1 safety model:

- Create only disposable local repositories.
- Require valid `.branchdojo.json` metadata for `check`, `hint`, and `reset`.
- Refuse unsafe paths.
- Refuse non-empty target directories for new exercises.
- Configure Git identity only inside generated exercise repositories.
- Avoid global Git config changes.
- Use explicit Git command arguments.

## Test Strategy

Each v0.2 exercise should add integration coverage for:

- Exercise creation and generated metadata.
- Initial `check` failure before solving.
- Human and JSON check output shape.
- At least one valid solution.
- Warning cases for acceptable but non-ideal history shape where applicable.
- Dirty working tree and active operation failure paths where relevant.
- Safe reset behavior.

Unit coverage should be added for shared validation helpers when new helpers are introduced.

## Release Criteria

v0.2 should be releasable when:

- All planned v0.2 exercises are implemented or explicitly deferred in public docs.
- `branchdojo list` accurately reflects available exercises.
- All generated exercise READMEs match actual validator behavior.
- `cargo fmt --check` passes.
- `cargo clippy -- -D warnings` passes.
- `cargo test` passes.
- GitHub Actions CI passes.
- The changelog summarizes the final v0.2 scope.
