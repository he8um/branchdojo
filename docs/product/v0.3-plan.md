# v0.3 Development Plan

## Status

Planning baseline. No v0.3 features are implemented yet.

## Objective

Improve the usefulness of the existing local Git kata experience without changing BranchDojo's product identity.

## Product Theme

Better feedback, better practice artifacts, and stronger exercise metadata.

## Target Users

- Developers practicing Git recovery workflows independently.
- Bootcamp students and mentors reviewing practice results.
- Onboarding programs that want repeatable local Git drills.
- Teams that want lightweight practice artifacts without remote services.

## Problems to Solve

- Static hints do not react to obvious repository state.
- Human output is useful at the terminal but hard to save for review.
- Exercise metadata exists in several places and should become more consistent.
- First-time users need clearer practice guidance and learning order.

## Proposed Scope

- Progress-aware hints.
- Optional Markdown check reports.
- Richer exercise metadata.
- README and onboarding polish.

## Explicit Non-Goals

- GUI or TUI.
- GitHub integration.
- Remote repository workflows.
- External exercise pack loading.
- Command-history tracking.
- Shell-history inspection.
- Analytics or telemetry.
- Global Git configuration changes.
- Crates.io publishing.
- Release automation.
- New exercises unless explicitly added to scope later.

## Feature 1: Progress-Aware Hints

### Purpose

Make `branchdojo hint --path <path>` more useful by incorporating current repository state while remaining deterministic and local.

### Behavior

Hints should still be concise and exercise-specific. The first hints may be state-aware when common blockers are detected:

- Dirty working tree: mention committing, stashing, or cleaning pending changes.
- Wrong branch: mention the expected branch for the exercise.
- Conflict markers: mention unresolved conflict markers.
- Active Git operation: mention completing or aborting the active operation.
- Missing expected branch or file: mention the missing final-state requirement.

### Examples

- `conflict-basic`: if conflict markers remain, hint says to remove markers and keep both required lines.
- `stash-switch`: if the working tree is dirty on `main`, hint says to preserve local work before switching.
- `detached-head-recovery`: if HEAD is detached, hint says to create `recovery/detached-work` from the current commit.

### Constraints

- Do not inspect shell history.
- Do not track exact commands.
- Do not require network access.
- Do not mutate the repository while generating hints.
- Keep output stable enough for tests.

### Validation/Safety Impact

Progress-aware hints should read the same repository facts validators already inspect. They should not weaken validation or introduce new safety exceptions.

### Test Strategy

- Unit-test shared hint-state analysis if introduced.
- Integration-test representative state-aware hints for dirty trees, wrong branches, conflict markers, detached HEAD, and missing branches.
- Regression-test static hints for all six released exercises.

## Feature 2: Report Output Files

### Purpose

Allow users and instructors to save check results as a review artifact.

### CLI Proposal

```bash
branchdojo check --path <path> --report <file>
```

`--json` should continue to print JSON to stdout. Report output should be opt-in and should not change validation semantics.

### Output Format Proposal

Markdown first:

- Exercise ID.
- Overall status.
- Score.
- Required checks.
- Warning checks.
- Next steps.
- Timestamp if a deterministic policy is chosen for generated reports.

JSON file export can remain future work because stdout JSON already exists.

### File Safety Rules

- Do not write a report unless `--report` is explicitly provided.
- Refuse unsafe report paths such as home, root, system directories, and parent directory targets.
- Prefer refusing to overwrite existing files unless a future `--force` option is added.
- Do not write inside `.git`.
- Surface clear errors if the report cannot be written.

### Test Strategy

- Integration-test Markdown report creation.
- Test refusal for existing files if overwrite is disallowed.
- Test unsafe report paths.
- Test that validation status and stdout behavior remain unchanged.
- Test report content for `PASSED`, `WARNING`, and `FAILED` outcomes.

## Feature 3: Exercise Metadata Improvements

### Purpose

Make exercise definitions more consistent and useful across listing, hints, reports, generated READMEs, and documentation.

### Proposed Metadata Fields

- `id`
- `title`
- `difficulty`
- `category`
- `estimated_time`
- `skills`
- `description`
- `starting_branch`
- `expected_final_branch`
- `introduced_in`
- `files`
- `branches`

### Internal Representation

Metadata can remain hardcoded in Rust for v0.3. External exercise packs remain future work unless explicitly moved into scope.

### Docs Impact

- Exercise docs should map cleanly to metadata fields.
- `branchdojo list` may show improved metadata columns.
- Generated READMEs should use metadata consistently.

### Test Strategy

- Unit-test metadata completeness.
- Integration-test `branchdojo list` output.
- Regression-test generated `.branchdojo.json` and `README.branchdojo.md`.

## Documentation Polish

- Add a concise "how to practice" section to README.
- Add a recommended learning path across the six released exercises.
- Add examples for reading `PASSED`, `WARNING`, and `FAILED`.
- Keep advanced exercise planning separate from released exercise docs.

## Implementation Order

1. Exercise metadata improvements.
2. Progress-aware hints.
3. Check report output.
4. Documentation and release polish.

Metadata comes first because it can support better hints, reports, generated READMEs, and listing output.

## Release Criteria

- v0.3 scope is accurately reflected in README, roadmap, and changelog.
- Existing six exercises retain current behavior.
- State-aware hints are deterministic and tested.
- Report writing is explicit, safe, and tested.
- Metadata is complete for all released exercises.
- No command-history tracking is introduced.
- `cargo fmt --check` passes.
- `cargo clippy -- -D warnings` passes.
- `cargo test` passes.
- CI passes on `main`.

## Open Decisions

- Should progress-aware hints be implemented per exercise or through shared check-state analysis?
- Should reports be Markdown-only in v0.3, or Markdown plus JSON file export?
- Should `branchdojo list` show metadata columns like difficulty and category?
- Should exercise metadata stay hardcoded in Rust for v0.3?
- Should v0.3 include any new exercise, or stay focused on feedback and reporting polish?
- Should report writing refuse existing files by default unless `--force` is later added?
- Should report paths be restricted to avoid unsafe locations?

## Risks

- State-aware hints could drift from validator behavior if they duplicate logic.
- Report writing introduces file-output safety requirements.
- Metadata refactors could churn existing exercise setup code.
- README additions could overpromise if planned features are described as available.

## Deferred Items

- GUI or TUI.
- GitHub integration.
- External exercise packs.
- Advanced exercises such as `interactive-rebase-basic`, `bisect-basic`, `merge-vs-rebase`, and `tag-release-fix`.
- Analytics or telemetry.
- Release automation.
