# BranchDojo v0.4 Plan

## Status

Released as v0.4.0 on 2026-07-10.

## Objective

Expand BranchDojo from beginner and intermediate recovery workflows into advanced Git practice while preserving safe disposable repositories and final-state validation.

## Product Theme

Advanced Git practice and reusable exercise foundations.

## Target Users

- Developers who have completed the beginner and intermediate exercises.
- Developers practicing history cleanup, release repair, and diagnostic workflows.
- Mentors and onboarding programs that want a clearer learning path.
- Teams that need local practice artifacts without dashboards or remote tracking.

## Problems To Solve

- The current catalog stops before advanced workflows such as rebase cleanup, bisection, release tags, and merge strategy comparison.
- Exercise ordering is visible in docs but not expressed as a clear learning path.
- The metadata model may need an `advanced` difficulty before advanced exercises ship.
- Future exercise packs and custom definitions need research, but not implementation, before the design can stay safe.

## Frozen Scope

- `interactive-rebase-basic`.
- `tag-release-fix`.
- `merge-vs-rebase`.
- `advanced` difficulty support.
- Documentation-only beginner, intermediate, and advanced learning paths.
- Validator, hint, report, and CLI documentation compatibility for the advanced exercise set.

## Explicit Non-Goals

- No GUI or TUI.
- No GitHub integration.
- No remote repository workflows.
- No telemetry or analytics.
- No classroom dashboard.
- No external exercise pack loading.
- No custom exercise parser.
- No YAML, TOML, or JSON exercise definitions.
- No crates.io publishing unless separately planned.
- No shell-history or command-history tracking.
- No global Git config changes.
- No unsafe repository mutation outside BranchDojo workspaces.
- No report templates.
- No PDF or HTML reports.

## Implemented Exercise 1: interactive-rebase-basic

### Purpose

Practice cleaning up local history by squashing or rewording commits before sharing work.

### Starting State

A disposable repository contains `main` and `feature/profile-copy`. The feature branch has useful profile copy, a `debug.txt` file, a WIP/debug commit, a typo fix, and a final polish commit.

### User Task

Clean the feature branch history while preserving the intended final profile copy.

### Expected Final State

The user is on `feature/profile-copy`, the working tree is clean, `profile.txt` has the final profile copy, `debug.txt` is absent, and WIP/debug history is not reachable from the final feature branch.

### Required Checks

- Valid BranchDojo metadata exists.
- Repository is on `feature/profile-copy`.
- Working tree is clean.
- No active Git operation remains.
- `main` and `feature/profile-copy` exist.
- Expected final content exists.
- Debug file/content is absent.

### Warning Conditions

- Final content is correct but WIP/debug commit subjects remain reachable.
- Final content is correct but history shape is broader or noisier than expected.

### Risks

Interactive rebase is command-sequence-heavy. Validation must stay focused on final repository state and observable history shape.

### Test Strategy

Integration tests cover setup, starting failure, clean-history pass, messy-history warning, wrong branch, dirty working tree, debug content, missing profile content, hints, reports, and reset.

## Deferred Exercise Candidate: bisect-basic

### Purpose

Practice finding the commit that introduced a regression using a deterministic local failure signal. Deferred to v0.5 or later.

### Starting State

A repository contains a linear history where one commit changes a small file from a passing state to a failing state.

### User Task

Identify the bad commit and record the result in a required file or branch state without relying on external test infrastructure.

### Expected Final State

The repository records the expected bad commit identifier or subject in a local file, returns to the expected branch, and has a clean working tree.

### Required Checks

- Valid BranchDojo metadata exists.
- Repository is on the expected branch.
- Working tree is clean.
- No active Git operation remains.
- The recorded bad commit matches the seeded regression commit.
- Expected files remain intact.

### Warning Conditions

- The bad commit is correctly identified but the repository is left on a detached HEAD or unexpected branch.
- The final state is correct but includes extra diagnostic files.

### Risks

`git bisect run` often uses scripts. BranchDojo should avoid requiring shell scripts and keep any failure signal inspectable through repository state.

### Test Strategy

Keep the regression signal file-based and deterministic. Add tests for correct identification, wrong commit identification, detached HEAD cleanup, and no-regression behavior for existing exercises.

## Implemented Exercise 3: merge-vs-rebase

### Purpose

Practice updating and integrating a feature branch while preserving both mainline and feature work.

### Starting State

A repository contains `main` and `feature/pricing-copy`. `main` received checkout trust copy after the feature branch was created, while `feature/pricing-copy` received two pricing copy commits.

### User Task

Bring `feature/pricing-copy` up to date with `main`, integrate the feature into `main`, preserve both files' expected content, prefer a clean linear integration, and leave the repository clean on `main`.

### Expected Final State

The user is on `main`, the working tree is clean, `main` contains both the pricing page and checkout trust copy, and `feature/pricing-copy` still contains the pricing feature copy.

### Required Checks

- Valid BranchDojo metadata exists.
- Repository is on `main`.
- Working tree is clean.
- No active Git operation remains.
- `main` and `feature/pricing-copy` exist.
- `main:pricing.txt` contains the pricing title, headline, FAQ title, and FAQ copy.
- `main:checkout.txt` contains the checkout trust copy.
- `feature/pricing-copy:pricing.txt` contains the pricing headline and FAQ copy.

### Warning Conditions

- Final content is correct but a merge commit was used.
- Final content is correct but `feature/pricing-copy` was not updated with the mainline checkout work.
- Final content is correct but the seeded feature commit subjects are not reachable from `main`.
- Final content is correct but the expected history order is not ideal.

### Risks

History-shape validation must remain observable and tolerant without tracking the exact command sequence.

### Test Strategy

Integration tests cover setup, starting failure and JSON shape, linear-history pass, merge-commit warning, wrong branch, dirty working tree, missing pricing content, missing checkout content, missing feature branch, hints, reports, and reset.

## Implemented Exercise 4: tag-release-fix

### Purpose

Practice correcting a local release tag that points to the wrong commit after a release-blocking fix.

### Starting State

A repository contains `main`, a `v1.0.0` tag created too early on a release candidate commit, and a later release-blocker fix commit.

### User Task

Move or recreate the local `v1.0.0` tag so it points to the fixed release commit.

### Expected Final State

The user is on `main`, the working tree is clean, `v1.0.0` points to a commit containing `release_blocker=false` and `release_ready=true`, and the tagged commit does not contain `release_blocker=true`.

### Required Checks

- Valid BranchDojo metadata exists.
- Repository is on `main`.
- Working tree is clean.
- No active Git operation remains.
- `main` exists.
- Corrected release content exists.
- Expected tag exists and points to the corrected commit.
- Incorrect release content is absent.

### Warning Conditions

- A lightweight tag is used when the exercise prefers an annotated tag.
- The tag points to correct content but tag message is missing or not ideal.
- The tag points to correct content but not directly to the seeded fix commit.

### Risks

Tag validation must be precise without requiring remote operations, publishing, or tag force-push behavior.

### Test Strategy

Integration tests cover setup, starting failure, annotated-tag pass, lightweight-tag warning, missing tag, wrong tag target, wrong branch, dirty working tree, missing fixed content, hints, reports, and reset.

## Learning Path Plan

- Beginner path: `conflict-basic`, `revert-mistake`, `wrong-branch-commit`.
- Intermediate path: `stash-switch`, `cherry-pick-basic`, `detached-head-recovery`.
- Advanced path: `interactive-rebase-basic`, `tag-release-fix`, `merge-vs-rebase`.

Learning paths should be documentation-only in the planning baseline.

## Exercise Metadata Impact

v0.4 includes:

- `advanced` difficulty.
- Stable category names for advanced workflows.

Metadata changes should be minimal and tested for catalog drift.

## CLI Impact

No CLI changes are planned in the baseline. Possible future additions, such as filtering `branchdojo list` by difficulty or category, require separate design and tests.

## Validation Impact

Advanced exercises should continue to validate final repository state and observable history shape, not exact command sequence.

Validators may need new exercise-specific checks for cleaned history, tag target, bad commit identification, or integration style.

## Safety Impact

v0.4 must preserve the existing safety model:

- Work only inside BranchDojo-created disposable repositories.
- Refuse unsafe paths.
- Refuse non-BranchDojo workspaces for check, hint, reset, and reports.
- Use explicit Git command arguments.
- Do not modify global Git config.
- Do not require shell scripts.

## Testing Strategy

- Unit-test metadata additions.
- Integration-test setup for each selected advanced exercise.
- Integration-test failing starting state, passing solved state, and warning shape.
- Preserve report and JSON output compatibility.
- Preserve progress-aware hints for all released exercises.
- Keep no-regression tests for all nine exercises.

## Release Criteria

- v0.4 scope is accurately reflected in README, roadmap, and changelog.
- Selected advanced exercises are implemented and documented.
- All nine exercises retain current behavior.
- New validators preserve final-state validation.
- Hints and reports work for new exercises.
- `cargo fmt --check` passes.
- `cargo clippy --all-targets --all-features -- -D warnings` passes.
- `cargo test` passes.
- CI passes on `main`.

## Open Decisions

- Should `branchdojo list` later support filtering by difficulty or category?
- Should external exercise packs be deferred to v0.5 or later?
- Should custom exercise definitions use Rust-only modules for now?
- Should `bisect-basic` be included, given it requires deterministic test behavior?

## Risks

- Advanced workflows can push the product toward command-sequence validation.
- Bisect scenarios can drift into script execution if not carefully scoped.
- External exercise-pack research could overtake built-in exercise quality.
- Learning-path metadata could become premature CLI surface area.

## Deferred Items

- JSON report files.
- HTML and PDF reports.
- Report templates.
- Dashboards.
- `--force` report overwrite behavior.
- External exercise packs.
- Custom exercise definitions.
- TUI or GUI.
- GitHub integration.
- Release automation.
